# M1 引擎重构说明（Java 21 + JavaFX 21）

> **M1（2026-10-17）**：本文档记录里程碑 M1「基础底座与引擎重构」中六个已复现缺陷的症状、真实根因、
> 修复方案与验证方式，并补充平滑滚屏摄像机、60×45 地图扩展与构建环境的取舍说明。
> 本文档面向后续维护者，回答「为什么现在是这个样子」；安装与启动方式请以 [README.md](../README.md) 为准。

---

## 一、六个已复现缺陷

### 缺陷 1：敌人每一帧都攻击（约 60 次/秒）

- **症状与复现**：进入战斗后不操作，敌人跟随渲染帧率每帧出手（60 FPS 下约 60 次/秒），
  玩家血量在 1 秒内从 100 掉到约 43。
- **真实根因**：旧 `GameEngine.updateBattle` 每帧无条件调用 `battleService.enemyAttack(...)`，
  而 `BattleService` 里没有任何「轮到谁行动」的概念，敌人攻击完全跟随渲染节拍执行。
- **修复方案**：`BattleService` 引入 `Turn`（`PLAYER` / `ENEMY`）行动权状态机——
  玩家行动成功才 `handOverToEnemy()`，`enemyAttack()` 只在 `turn == ENEMY` 时结算一次并交还玩家。
  引擎仍然可以每帧无脑调用，但敌人只会打一次。这是机制上的修正，不是冷却时间补丁。
- **验证方式**：`BattleServiceTest.enemyDoesNotAttackWhilePlayerHoldsTheTurn`（行动权在玩家手里时
  连打 600 帧血量不变）与 `enemyAttacksExactlyOncePerPlayerAction`（一次玩家行动只还击一次）。

### 缺陷 2：战斗中无法逃跑

- **症状与复现**：进入战斗后按 ESC 逃跑无效，玩家被永远锁在战斗里。
- **真实根因**：旧实现没有把「逃跑成功」与「退出战斗 / 离开敌人所在格」衔接起来——即使结算了逃跑，
  玩家仍停在敌人所在格，下一帧立刻重新触发同一场战斗（原地重触发）。
- **修复方案**：`BattleService.tryEscape()` 返回 `EscapeResult`。成功时引擎调用 `retreatAfterEscape()`，
  由 `RetreatPlanner.escapeDestination()` 计算安全落点（优先退回触发战斗前的那一格，被占或被堵则螺旋
  搜索最近可通行格），结束战斗并把玩家挪过去；失败时把行动权交给敌人，敌人只还击一次，不允许无限重试。
- **验证方式**：`BattleServiceTest`（成功/失败/非玩家回合三种结果）、
  `RetreatPlannerTest`（`prefersTheTileThePlayerCameFrom` / `neverReturnsTheEnemyTile` /
  `destinationIsAlwaysWalkable` 等）。

### 缺陷 3：单次击杀重复结算经验（双倍经验）

- **症状与复现**：同一个敌人被击杀一次，玩家却获得双倍经验。
- **真实根因**：旧实现在大地图攻击路径与战斗内击杀路径两处各自调用
  `player.gainExp(enemy.getExpReward())`，同一个敌人只要在两处都满足 `!isAlive()` 就被结算两次。
- **修复方案**：经验发放收敛到全工程唯一入口 `BattleService.grantDefeatReward()`，并由
  `Enemy.claimDefeatReward()` 提供幂等护栏——每个敌人实例只可能成功领取一次，重复调用返回 `false`。
- **验证方式**：`BattleServiceTest.defeatRewardIsGrantedExactlyOnce` /
  `overworldKillAndBattleKillCannotBothGrantReward`；引擎级 `GameEngineRegressionTest`
  断言三只敌人 20+35+50=105 经验恰好升到 2 级并余 5，不翻倍。

### 缺陷 4：存档没有写入地图表，读档后地图被重新随机

- **症状与复现**：F5 存档后重开游戏再 F9 读档，地图与存档时不一致（被重新随机）。
- **真实根因**：旧实现只把玩家与敌人写进数据库，地图完全没有落盘；`loadGame` 只能还原玩家与敌人，
  地图对象仍是内存里那张（重开游戏则重新随机）。
- **修复方案**：新增 `map_meta`（尺寸 / 种子 / 地块数）与 `map_tile`（逐格地块）两张表；存档在一个事务里
  删除四张表旧数据后整体写入，失败回滚；读档先把玩家 / 敌人 / 地图全部读进临时变量并校验
  （地图行数必须等于 width×height、元信息合法），校验通过后才写回传入对象——缺少地图行的旧存档整体拒绝，
  绝不半加载或用随机新地图冒充。
- **验证方式**：`SaveLoadServiceTest.saveLoadRoundTripIsLossless` /
  `legacySaveWithoutMapTablesIsRejectedWholesale` / `incompleteMapIsRejected`；
  存档与读档各打印一次 `tileHash()`，读档后哈希一致即证明地图未经重新随机（F3 调试面板可复看哈希）。

### 缺陷 5：草地贴图每帧重新随机，画面持续闪烁

- **症状与复现**：站在大地图上静止不动，草地方块的草叶、土斑、小花每一帧都在变，画面持续闪烁。
- **真实根因**：旧 `renderTile` 在渲染路径里每帧调用 `random.nextInt(...)` 决定草叶位置，每帧重新抽签。
- **修复方案**：所有装饰细节（草叶、明暗阶、裂纹、水波相位、小花）在构造期由种子确定性烘焙进 `detail[][]`；
  渲染期只读取既定数值，运行期不再有任何 `Random` 调用，逐帧完全一致。地图生成一次后即为只读
  （没有 `setTile`，从 API 层面保证）。
- **验证方式**：`GameMapTest.sameSeedProducesIdenticalMap` / `decorationIsStableAcrossReads` /
  `tileHashCoversSizeAndSeed`；同一 seed 的 `tileHash()` 相同。

### 缺陷 6：快速连续按键被吞掉

- **症状与复现**：快速连按移动键或技能键，部分短按（在两次渲染帧之间完成的「按下→释放」）被吞掉。
- **真实根因**：旧实现把「刚按下」记录在 `Map<KeyCode,Boolean> justPressed` 里，而释放回调立刻写入
  `false`，于是两次渲染帧之间完成的短按会被后到的释放事件抹掉，逻辑层永远看不到它。
- **修复方案**：改为有序缓冲 `InputHandler`——按下时把键追加进 `pending` 队列（`held` 集合过滤系统自动重复），
  `beginFrame()` 把队列整体搬进本帧事件表；`isKeyJustPressed` 只查询不消费，同一帧多处可见；
  `deferToNextFrame` 支持把未处理完的按键退回下一帧。
- **验证方式**：`InputHandlerTest.tapBetweenFramesIsNeverLost` /
  `releaseAfterFrameDoesNotEraseTheEvent` / `rapidTapsInOneFrameAreAllRecordedInOrder` 等。

## 二、两个结构性问题的解决

### 摄像机跟随（地图 960px 高 vs 窗口 720px）

旧地图 40×30 = 1280×960 像素，窗口只有 1280×720，下方 240px 永远看不到，也没有任何摄像机。
M1 引入 `core/Camera.java` 平滑跟随玩家并把视口夹在地图边界内，同时地图扩展到 60×45（见下节），
走到地图边缘不再切黑、不再露出黑边。

### `GameState.MENU` 声明了却从未进入

旧版枚举里声明了 `MENU` 但启动后直接进入 `PLAYING`，从未使用。M1 把状态机接成
`MENU → CHAR_SELECT → PLAYING ⇄ {PAUSED, BATTLE} → {VICTORY, GAME_OVER}`：
启动进入标题画面（MENU），选角后进入大地图。

## 三、平滑滚屏摄像机与 60×45 地图的设计权衡

### 平滑跟随：指数趋近

镜头采用帧率无关的指数趋近 `x += (target - x) * (1 - exp(-dt / TAU))`，时间常数 `TAU = 0.12` 秒。

- **优点**：对任意 `dt` 都收敛、不会过冲；低帧率下不会把差值一次性补上造成跳变。
- **权衡**：`TAU` 越小越「跟手」但越硬，越大越「飘」但越平滑；0.12 是两者的折中。指数趋近永远
  只是渐进逼近，不会完全瞬时到位（`isSettled()` 用 0.5px 阈值判定「已到位」）。

### 视口夹取与整数偏移

- 镜头把偏移限制在地图范围内（`clamp`），贴边时自动夹取，不会露出画布黑边；地图小于视口时固定 0。
- 渲染只使用 `getRenderX() / getRenderY()` 的**整数**偏移，保证像素画不会被半像素采样拉糊。
  **权衡**：平滑过程中存在 ≤1px 的取整抖动，换来的是所有精灵与地块的硬边缘。

### 60×45 地图 + 视口裁剪

- 地图从 40×30 扩展到 60×45 = 1920×1440 像素（每格 32×32），窗口 1280×720，世界明显大于视口。
- `GameMap.visibleRange()` 每帧只算出可见地块窗口（闭区间），`render` 只绘制该窗口而不是遍历整张地图。
  **权衡**：地图越大、一次性生成与哈希校验的成本越高，但生成期一次性完成、游玩期只读，
  换取的是「读档后地图逐格一致」与「渲染只画可见部分」的确定性。

## 四、构建环境陷阱：JDK 21 必须带 `bin/javac`

- **坑点**：`/usr/lib/jvm/java-21-openjdk-amd64` 这类目录**可能只有 JRE、没有 `bin/javac`**，
  选中它会报 `release version 21 not supported`。判断方法：
  ```bash
  ls /path/to/jdk/bin/javac && /path/to/jdk/bin/java -version
  ```
- **已验证工具链**：Liberica 21 + 内置 JavaFX（`/home/Yuhang/.sdkman/candidates/java/21.0.12-fx+1.1-librca`），
  该目录同时带 `bin/javac` 与 `bin/java`。
- **`run.sh` 的解析与校验**：脚本按「已知可用 JDK → SDKMAN current → `$JAVA_HOME` → PATH → SDKMAN →
  `/usr/lib/jvm` → 其它常见位置」的顺序收集候选，逐个校验「`bin/javac` 存在 且 `java -version` 报告 21+」，
  自动跳过只有 JRE 的目录；一个可用 JDK 都找不到时打印明确的安装/修复指引并以非零码退出，
  不会带着错误的 JDK 硬跑。
